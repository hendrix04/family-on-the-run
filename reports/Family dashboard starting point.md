# Family dashboard starting point

**I recommend one hosted Go backend, SQLite, and an embedded touchscreen web interface.** Start with ordinary HTML/CSS, a small amount of JavaScript, and FullCalendar Standard for the weekly and monthly views. Go can embed those assets into the executable, and `modernc.org/sqlite` provides a CGo-free SQLite driver with documented Windows, macOS and Linux targets. This is a recommendation based on your priorities, rather than a benchmark or an implementation already built here. ([Go embedding](https://pkg.go.dev/embed), [SQLite driver and targets](https://pkg.go.dev/modernc.org/sqlite), [FullCalendar integration](https://fullcalendar.io/docs/vanilla-js))

Your clarification makes the architecture much easier to choose: **share the hosted backend now; let frontends diverge later.** That server should own family tasks, future food data, calendar connections and the event cache. Deploy one household server instance with persistent storage for its database, tokens and backups. The wall browser and eventual phone clients should use the same HTTP API. You can build a useful Home screen without selecting a native mobile framework first. The recommended frontend still uses JavaScript; Go is the backend choice, not a way to remove JavaScript from browser rendering.

Interpret “single standalone binary” as **one application executable per OS/CPU**, with the UI assets inside it. Go builds select `GOOS` and `GOARCH`; one executable does not run unchanged across every platform. Persistent SQLite data, configuration, tokens and backups remain separate mutable files, and the touchscreen needs a browser. With embedded frontend files, the proposal requires neither a runtime Node.js service nor a separate database server. This backend can run on a home machine or a hosted machine; clients connect to that instance rather than each maintaining their own family database. ([Go build targets](https://go.dev/doc/install/source#environment), [Go embedding](https://pkg.go.dev/embed), [SQLite driver](https://pkg.go.dev/modernc.org/sqlite))

I would briefly inspect Mantel and Donetick, then build the small requested application around reusable libraries. Replacing a Python backend just to obtain Go packaging discards much of a fork's advantage. Keep license boundaries explicit: MIT code requires preserving its notices; copying Donetick's AGPL code brings its distribution and network-source obligations, rather than allowing it to become MIT by changing your project license. Use it for workflow inspiration rather than a mandatory side service. OpenFamHub's documented dependence on Todoist and Mealie makes it a less suitable foundation for your independent system. Prism and Kinboard use PolyForm Noncommercial licensing; that restriction differs from the OSI definition's allowance for use in any field, including business. These frameworks' platform support does not prove that their default controls supply your weekly/monthly event interface. FullCalendar already documents month, timed week/day and list views, plus touchscreen interactions, which is why I favor the web UI for this first milestone. Standard plugins are MIT; your daily agenda plus four task columns requires ordinary layout, not premium calendar resource columns. Embed the library files locally. ([FullCalendar views](https://fullcalendar.io/docs), [Touch support](https://fullcalendar.io/docs/touch), [Licensing](https://fullcalendar.io/license))

Your Shopify example is current: its **September 10, 2026** announcement says it is moving mobile apps from React Native back to Swift/Kotlin; Shop has shipped native and the Shopify app migration is underway. Shopify attributes the changed economics partly to coding agents and platform-specific advantages, while acknowledging that two-platform maintenance still takes effort. That is evidence for allowing frontend divergence, rather than a reason to implement two phone apps before your dashboard works. ([Shopify announcement](https://shopify.engineering/back-to-native))

The proposed API leaves Flutter eligible as a later client too. Its Windows distribution requires executable, DLL and data files, so it does not provide a lone desktop executable in the same sense as the proposed server; that no longer prevents its use when the binary requirement concerns backend deployment. ([Flutter Windows distribution](https://docs.flutter.dev/platform-integration/windows/building))

**For Google Calendar, begin read-only and choose the simplest acceptable connection.** My suggested first option is each calendar's **Secret address in iCal format**, fetched only by the backend. Google documents this as a view-only subscription, distinct from a public calendar, and says to keep the URL private. Some work/school administrators hide it. Keep creating/editing events in your existing Google interface for this first version. ([Google subscription help](https://support.google.com/calendar/answer/37648?hl=en))

ICS avoids OAuth onboarding when the needed feeds are available, but it is polling-based and supplies no documented freshness guarantee in that help page. ([Google subscription help](https://support.google.com/calendar/answer/37648?hl=en)) Show the last successful refresh, retain cached events on failure and indicate stale data. Validate the real feeds before committing: recurring events, exceptions/cancellations, all-day dates, time zones and daylight-saving boundaries should be explicit acceptance cases. This is a proposed test set, not a claim that a selected parser already handles it.

If those feeds are unavailable, calendar discovery is important, or wall event editing is needed, use **Google's web-server OAuth flow on the hosted backend**. Keep tokens there. `CalendarList.list` discovers an account's calendars; `Events.list` fetches a specific calendar. Multiple calendars accessible to one account can therefore share one authorization; independent accounts need their own authorization or shared access. For viewing, investigate event/calendar-list read-only scopes; add event-write permission when implementing editing. ([Web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server), [Calendar list](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list), [Events](https://developers.google.com/workspace/calendar/api/v3/reference/events/list), [Scopes](https://developers.google.com/workspace/calendar/api/auth))

FullCalendar's Google plugin documents public-calendar/API-key access, so use your backend's JSON event feed for private calendars. For an open-source release, decide between operator-supplied OAuth credentials and an appropriately configured project registration. Google's verification requirements depend on use and scopes; External projects left in Testing generally expire Calendar refresh tokens after seven days. These are onboarding constraints to resolve, not reasons to make family calendars public. ([FullCalendar Google plugin](https://fullcalendar.io/docs/google-calendar), [JSON feeds](https://fullcalendar.io/docs/events-json-feed), [Verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification), [Token expiration](https://developers.google.com/identity/protocols/oauth2#expiration))

**Begin with one complete household workflow.** Build the left tabs exactly as requested: Home, Weekly Calendar, Monthly Calendar, Food and House. Home should contain, from left to right, **Daily Calendar, Lindsay To Do, Matt To Do, Carter To Do and Sydney To Do**. Use a simple HTML daily agenda and four task lists supporting add, edit and complete. Store configurable household/person records, seeded with these names. Food can initially be a placeholder; House can display the static recurring chore schedule.

Then connect the real calendars and use one shared event representation for daily, weekly and monthly views. Test on the actual 23.8-inch touchscreen early. Its 2560×1440 physical resolution does not establish the CSS viewport because device scaling and zoom affect pixel ratios. Measure `window.innerWidth`/`window.innerHeight`, check five-column readability and scrolling, and aim for generously spaced primary controls around 48–56 CSS pixels as a design choice. WCAG's enhanced target-size benchmark is 44×44 CSS pixels, subject to exceptions. ([MDN pixel ratios](https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio), [W3C target sizes](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced))

Plan authentication with the hosted backend, require it before internet exposure, then try a phone browser and verify shared task changes across two clients. A shared backend does not automatically provide offline synchronization; defer that separate problem until needed. Build Food one useful workflow at a time: dinner planning and a manual grocery list, followed by recipes. Let a demonstrated need for notifications, camera integration or app-store delivery determine any native client. The first release decision should be whether the family reliably sees today's events and completes its tasks on this screen.
