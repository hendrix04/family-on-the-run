# Existing family dashboards, reusable components, and Google Calendar integration

## Which existing projects are close enough to adopt or fork?

### Takeaway

The strongest calendar-first trial is **Mantel**, and the strongest single-binary architecture/task reference is **Donetick**. My recommendation is to inspect these briefly, then build the requested small dashboard using reusable calendar UI rather than combine independent services; this is a judgment based on the feature and distribution differences below, not a claim that these applications were tested locally. The user later clarified that frontends may diverge and a **single hosted backend** is desirable; the single binary therefore principally concerns backend deployment, with one touchscreen web client first and possible native mobile clients later.

### Inferences

- Building a compact hosted Go application with embedded web assets is preferable if one distributed executable remains firm. Mantel/Family-Hub are valuable references, but replacing their Python backend for packaging would discard much of the benefit of a fork. Donetick aligns with packaging but adds a large chore product and still needs Google event and food features. With the user's hosted-backend clarification, the wall display can connect to that server through a browser, and later clients can share the same API.
- Keep a brief evaluation spike: inspect Mantel calendar interactions and Donetick's task completion/recurrence behavior, then reuse libraries in the new app. Do not start with a stack of Mealie + Donetick + separate calendar service; that architecture contradicts the stated independent single-binary outcome.
- MIT forks/components permit a range of project license choices while preserving their notices. Copying AGPL code changes the licensing conversation: follow the actual license's distribution and network-source requirements, and do not assume copied AGPL code can become MIT. [Donetick license](https://github.com/donetick/donetick/blob/develop/LICENSE.md), particularly sections 5, 6, 13, is the concrete source for those obligations.

### Gaps

- No candidate was run, touch-tested on the user's monitor, security-audited, or proven to handle all Google recurrence edge cases. README features are assertions by maintainers, not verified runtime results.
- Exact requested Home arrangement was not verified in a candidate. Google integration for Donetick was not established; its task calendar must not be described as Google calendar sync.
- No matching Go application named Matter was verified. Avoid inventing or conflating it with the Matter device protocol.

## Which components reduce implementation effort without creating mandatory side services?

### Takeaway

Use **FullCalendar Standard** for week/month/agenda rendering if choosing a web UI. Study specialized food/chores applications for behavior, but do not introduce them as required services for this standalone project.

### Cited Findings

- FullCalendar Standard is MIT; Premium adds resource columns, timelines and printing. [Pricing/license distinction](https://fullcalendar.io/pricing), [Premium plugins](https://fullcalendar.io/docs/premium). Its [DayGrid](https://fullcalendar.io/docs/daygrid-view), [TimeGrid](https://fullcalendar.io/docs/timegrid-view), and [List](https://fullcalendar.io/docs/list-view) cover month, timed week/day, and agenda views. [Touch documentation](https://fullcalendar.io/docs/touch) describes long-press selection/drag/resize.
- No premium resource view is needed for the proposed daily-calendar-plus-four-task-columns layout: those are ordinary dashboard columns, not five calendar resource columns. This is a design inference from the user layout and FullCalendar's documented distinction. Premium open-source licensing in v7 is AGPLv3 rather than v6 GPLv3; [v7 migration guide](https://fullcalendar.io/docs/upgrading-from-v6). Start on Standard unless a future feature actually needs premium.
- FullCalendar's [Google Calendar plugin](https://fullcalendar.io/docs/google-calendar) documents **public** Google Calendars with API-key access. It is not a private multi-account OAuth integration. Fetch private events in the application's backend and pass the calendar UI JSON instead; FullCalendar documents [JSON feeds](https://fullcalendar.io/docs/events-json-feed).
- **Mealie** offers recipe URL import, meal plans and shopping lists with a third-party API, under AGPLv3. [Repository](https://github.com/mealie-recipes/mealie). It is a Python backend / Vue application deployed with Docker, not a small embedded library. [pyproject](https://github.com/mealie-recipes/mealie/blob/mealie-next/pyproject.toml), [v3.28.0 release](https://github.com/mealie-recipes/mealie/releases/tag/v3.28.0), published 2026-09-24. Use it for feature/data-model inspiration, or an explicitly optional future adapter.
- **Tandoor Recipes** has recipes, meals and shopping, but its [README license section](https://github.com/TandoorRecipes/recipes#license) states AGPLv3 **with Commons Clause selling exception**. Do not report it as ordinary AGPL or assume its code is suitable for a generally reusable unrestricted fork. [License](https://github.com/TandoorRecipes/recipes/blob/develop/LICENSE.md).
- **Vikunja** demonstrates a Go service and web frontend bundled into a single deployable binary, with SQLite supported; [official install docs](https://vikunja.io/docs/installing/). Its desktop wrapper/mobile clients are separate ways of reaching the service, not evidence of a unified native UI. These docs explicitly describe the service as a web application. It is a task-product architecture reference, not a family-calendar/food solution.

### Inferences

- The first release can implement local assigned tasks directly, because the requested task interactions are limited (add/edit/complete for a named family member). Importing an entire chore/task server just to supply four columns would increase integration and licensing work. This is a scope recommendation, not an estimate of measured development time.
- Model House initially as a human-readable recurring schedule. Add recurrence execution/history only when the family wants that behavior. Donetick's due-date versus completion-date rules are useful product distinctions to decide later.
- Food should begin with recipe bookmarks/manual recipes, weekly dinner choices and a checked grocery list; automatic ingredient normalization/unit conversion is a later feature. Mealie/Tandoor are behavior references, not required infrastructure.

### Gaps

- No direct Mealie/Tandoor parser/library was verified as an embeddable Go package. Do not claim their import functionality is freely reusable without inspecting the exact code/license boundaries.
- FullCalendar touchscreen usability at the requested physical size still needs a prototype; library support does not establish that its default target sizes suit the display.

## What is the lowest-effort Google Calendar path, and what must a public project handle?

### Takeaway

For a display-first first milestone, accept each calendar's **secret iCal feed** and keep it server-side; this avoids an OAuth onboarding flow but is read-only and polling-based. If calendar edits or robust connected-account onboarding are required, use the Calendar API and OAuth, initially with read-only scopes for display.

### Cited Findings

- Google officially supports view-only subscription using the **Secret address in iCal format**. The feed is distinct from the public address, must remain private, and can be reset to invalidate old URLs. Work/school administrators may hide it. [Google Calendar Help](https://support.google.com/calendar/answer/37648?hl=en).
- Google does not promise an end-to-end feed freshness SLA in that inspected help page. The app can choose a poll interval and show last successful retrieval; do not promise instant iCal updates or repeat a generic 12/24-hour number without evidence for the particular producer/consumer. Google-to-dashboard fetching is different from Google importing a third-party calendar.
- Calendar API scopes include `calendar.readonly`, `calendar.events.readonly`, `calendar.calendarlist.readonly`; event writes can use `calendar.events`, whereas full `calendar` also permits calendar/share/delete administration. [Official scopes](https://developers.google.com/workspace/calendar/api/auth). For display plus a calendar picker, the narrower event/list read-only pair is a proposal; verify method scopes during implementation.
- [`CalendarList.list`](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list) returns calendars on the authenticated user's list. [`Events.list`](https://developers.google.com/workspace/calendar/api/v3/reference/events/list) takes a specific calendar ID. Thus multiple calendars accessible to one Google account can use one authorization, while independent accounts need their own authorization or shared access to a chosen display account. Permission roles affect visibility/editing: [ACL resource](https://developers.google.com/workspace/calendar/api/v3/reference/acl).
- For the user's clarified **hosted backend**, use Google's [web-server OAuth flow](https://developers.google.com/identity/protocols/oauth2/web-server), with registered callback URLs and tokens/credentials retained on the server. The touchscreen and eventual mobile clients reach the family backend rather than each owning a separate calendar token. This is the recommended architecture based on the clarified request.
- Google's alternative installed-app OAuth flow assumes distributed apps **cannot keep secrets**, supports PKCE, requires opening the system browser, and supports loopback redirects for desktop. It also documents embedded-user-agent errors. [Installed-app OAuth](https://developers.google.com/identity/protocols/oauth2/native-app). This matters only if distributing a locally installed backend that directly connects to Google; it is not the final OAuth recommendation for a hosted instance. Do not treat hiding a shared client secret inside a publicly distributed binary as a security solution.
- Personal use by only a few people known to the developer is an exception to Google sensitive-scope verification, though users may see an unverified-app screen and a user cap. Public distribution needs evaluating the actual scopes and verification process. [Sensitive scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification). A bring-your-own OAuth client is an onboarding option, but creates extra user effort; do not claim a permissive code license bypasses Google's OAuth requirements.
- For External OAuth projects in **Testing**, refresh tokens expire after seven days unless scopes are only basic identity scopes; Calendar access is not that exception. [Google OAuth token expiration](https://developers.google.com/identity/protocols/oauth2#expiration). Production publishing and app verification are distinct steps; do not promise publishing alone removes the unverified warning.
- Incremental event synchronization uses `nextSyncToken`, pagination and deletion records; invalid tokens require handling HTTP `410` and full resync. [Google synchronization guide](https://developers.google.com/workspace/calendar/api/guides/sync). For the earliest small display, a bounded date-window fetch is a simpler proposal; cache that range explicitly rather than represent unqueried dates as empty.
- Google API push notifications require an HTTPS callback with a valid certificate, per-resource subscriptions, expiring channels, and follow-up API requests for the changes; messages can be dropped. [Push guide](https://developers.google.com/workspace/calendar/api/guides/push). This is why polling is the recommended initial design for a LAN dashboard, rather than adding a publicly reachable webhook endpoint immediately.

### Inferences

- Proposed first integration: one configurable calendar feed per source, backend-only fetching, display colors, bounded window, configurable polling, last-success timestamp and a stale/offline indicator. Keep displaying cached schedule on fetch failure. Secret feed URLs should never appear in frontend bundles, screenshots, logs or source control.
- Validate display behavior for recurring events, moved/cancelled occurrences, all-day dates, timezone differences and DST boundaries; these are proposed acceptance checks, not claims that a selected library already passes them.
- Start read-only and continue creating/editing events using existing Google Calendar. Add API writes only when wall event entry is wanted. Use the same internal calendar source/event representation for the daily, weekly and monthly views; avoid separate calendar implementations.
- If several family calendars are already shared to one account, authorize that account once and expose a calendar selector. If accounts cannot share their calendars, support connecting more than one account. Account count must not be conflated with calendar count.

### Gaps

- Exact classification of each proposed narrow scope as sensitive versus non-sensitive was not directly shown in the inspected primary scope table. Verify the Google Cloud consent-screen classification when configuring the app; the linked verification requirements are confirmed conditional policy, not a claim that every calendar scope has identical classification.
- iCal feed freshness and availability for the family's actual accounts are untested. ICS avoids OAuth effort only when the needed secret feeds are available and read-only behavior is acceptable.
- No family Google accounts were accessed, no feed secrets requested, and no OAuth app configured during this research.
